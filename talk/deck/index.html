The problem

Reliability compounds against you

99% per step, after

10 steps  90%
100 steps  37%
1,000 steps  0.004%

Even 99.9% per step is 37% at 1,000.

"Every agent demo is short. Real work is long. Per-step accuracy multiplies, so the horizon eats you even when each step looks great." Pause on 37%.
How agents fail

Confidence is not evidence

Most failures aren't bad reasoning. They're the agent believing its own claim about the world.

"tests pass""file written""precondition met""safe to deploy""done"

Each is a claim about world state. None should count until something other than the model checks it.

Five flavors, one mechanism: the model asserts state and then acts on the assertion.
GATS · arXiv:2607.08894 · with Dymitr Nowicki

The model is the last resort, not the decider

UCB1 tree search over a persistent state-transition graph picks every action. Nothing in that loop calls a model.

Each predicted transition is answered by the cheapest layer that can answer it.

L1 symbolic contractsexact · free
L2 statistics from its own runslearned
L3 LLM prediction, cachednovel only

Projected open-domain split: 60% / 30% / 10%.

"Symbolic where you can, learned where you've seen it, neural only for the genuinely new. Episode one pays; episode two is free."

The inversion

Neural proposes, symbolic disposes

Typical agent

The model decides what to do, does it, checks it, and writes the report.

LLM → action → LLM → action → "done"

LEDGER

GATS picks every action. The model lives inside skills (writing a patch). Its output counts only after a sensor confirms it.

plan → skill(LLM) → sensor → journal

The model is a component, not the controller.
State

State is what sensors say

The repo is a set of propositions. Deterministic sensors produce them, never the model.

tests.pass:unitrepo.cleanpatch.applied:arecoverablebudget.llm:ok

Lie detection: claimed effects minus observed effects = an INCIDENT in the journal, and the planner routes around the falsified edge.

Verify after execute. A falsified edge resets its statistics; L2 learns the action is stochastic.
Safety

Safety is graph semantics

  • Risk classes gate execution, not search. Profiles: attended, supervised, autonomous.
  • Irreversible = an action that deletes the recoverable proposition.
  • A denial is an observation the planner routes around, not a crash.
  • Escalation has a named reason: gate_denied · budget_exhausted · no_path · infeasible
"Infeasible" matters most for the bench section: the agent is allowed to say the task can't be done as specified.

Thesis

Models are parts.
The harness is the product.

Swap Claude for a local 27B model and the guarantees don't move: state, verification, replay, the last mile.

Five predictions
  1. Agent evals report variance and replayability, not just success rate.
  2. Regulated industries require deterministic replay of agent actions.
  3. The LLM moves down the stack: skill author and last-resort predictor.
  4. Verifiers become the moat; models become interchangeable.
  5. "I can't do this as specified" becomes a scored capability.
The two laws

Context is the budget.
A runnable check is the finish line.

Law 1: context degrades as it fills

Every file read and command output lands in the window. As it fills, the agent drops early instructions: 40 files and six suite runs in, it ignores the "no mocks" rule from turn 2.

Law 2: a check closes the loop

Without a pass/fail signal, the agent stops when the work looks done, and you become the verifier. With one, it iterates until the check passes.

Every tip that follows either protects context or closes the verification loop.

Tip 1

Give every task a runnable check

# before fix the rate limiter, it lets too many requests through # after Write a failing test in tests/rateLimiter.test.ts that fires 101 concurrent requests and expects exactly 100 x 200 and 1 x 429. Confirm it fails, fix the race, run `pnpm test rateLimiter` until green. End with the test output.

A concrete repro, a test that fails first, a scoped command, and evidence demanded instead of a claim. To make it unskippable, put make check in a Stop hook: exit code 2 blocks the turn from ending until it passes.

"A check is the difference between watching a session and walking away from it." This is LEDGER's sensor idea, applied with a prompt and a hook.
Tip 2

Treat context as the budget

  • One task per session. /clear between unrelated tasks.
  • After two failed corrections, start fresh with a better prompt.
  • Send investigation to subagents so file dumps never enter the main thread.
  • Handoff: session bloated, work not done? Write state to disk and restart clean.
Use subagents to investigate how token refresh works and whether we have OAuth utilities to reuse. Return file:line refs and a 10-line summary.
Write HANDOFF.md: goal, files changed, decisions and why, approaches that failed and why, the exact next step, and the test command that proves it. # fresh session: @HANDOFF.md continue from the next step
Tip 3

Get a fresh-context review before "done"

The agent that wrote the code is biased toward it. Review with something that didn't write it:

/code-review subagenta second sessionCodex /review on Claude's branch
Use a subagent to review the diff against PLAN.md: every requirement implemented, edge cases tested, nothing out of scope. Report correctness gaps only.

Restrict findings to correctness and stated requirements, or you'll chase nitpicks into over-engineering.

Tip 4

Make repeated corrections durable

Correct the same thing twice? Encode it instead of correcting it a third time.

Judgment rule

One line in AGENTS.md. CLAUDE.md can just @AGENTS.md so both tools share it.

You hoisted the lazy import in workers/ twice. Propose the smallest one-line AGENTS.md change that would have prevented it, as a diff.

The problem

Risk-averse work asks different questions

Most agent evals ask

Did it usually work?
How often does it pass?

Payments, deploys, infra, regulated code ask

What exactly did it do?
Can you stop it before the bad step?
Can you prove it afterwards?

"In risk-averse work the question isn't 'did it usually work', it's 'can you show me exactly what it did, and could you have stopped it before the bad step.'"
The honest limit

Search over raw actions doesn't scale

Tested at |A| = 15, depth 20. Impractical past about 20 actions or depth 10.

So LEDGER searches over a few coarse plan-level actions and pushes the open-ended part down into skills.

This is the bridge from the paper to the product. The limit is the design constraint LEDGER was built around.
Actions

Two altitudes

Plan level: searched

RunSuite · AuthorPatch · ApplyPatch · Commit · PushBranch · CreatePR

Small, coarse, contracts known. This is what keeps search tractable.

Skill level: LLM inside

Writing the diff. Output is a proposal: preflight, git apply --check, then the suite decides.

The bench almost lied too

Audit the evaluator

  • Reruns after a harness fix score a harness tuned on that failure.
  • A hidden oracle encoded one algorithm's answer to a degenerate case. Calibrate against two implementations.
  • A task I called impossible, the model solved (primes, Claude backend, 10/10, earned).
  • Held-out tasks must be written after the harness is frozen, by someone not tuning it.
Harnesses are the RL environment

The harness already is the training rig

Sensors

= the verifier. Binary, deterministic rewards.

Worktrees

= rollout infrastructure.

Journal

= trajectory store, with per-action postconditions for credit assignment.

Three surfaces: the skill policy (RL with verifiable rewards), planner value nets (PUCT replacing UCB1), L2 as a learned dynamics model. Weights promoted only if plan variance stays at zero.

Two capabilities to score

"I can't do this as specified"

Benchmarks that only count passes reward test gaming. Ship impossible tasks in every suite; grade recognition and integrity.

Self-improvement, gated

ledger improve: LEDGER files its own bugs as failing tests and fixes them on a branch, local model only. Its gate caught 2 bad changes in 5; a human merges.

Safe only when the verifier sits outside the thing being improved.

The thinking-reply fix (a 10-line change raising an honest error instead of returning empty text) was authored by qwen3.8:27b alone on its second of four tries. One accepted commit in an earlier run was partly gamed: a wrong alias satisfied the lint check. That loophole is the lesson.
