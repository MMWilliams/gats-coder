The two laws

Context is the budget.
A runnable check is the finish line.

Law 1: context degrades as it fills

Every file read and command output lands in the window. As it fills, the agent drops early instructions: 40 files and six suite runs in, it ignores the "no mocks" rule from turn 2.

Law 2: a check closes the loop

Without a pass/fail signal, the agent stops when the work looks done, and you become the verifier. With one, it iterates until the check passes.

Every tip that follows either protects context or closes the verification loop.

Tip 1

Give every task a runnable check

# before fix the rate limiter, it lets too many requests through # after Write a failing test in tests/rateLimiter.test.ts that fires 101 concurrent requests and expects exactly 100 x 200 and 1 x 429. Confirm it fails, fix the race, run `pnpm test rateLimiter` until green. End with the test output.

A concrete repro, a test that fails first, a scoped command, and evidence demanded instead of a claim. To make it unskippable, put make check in a Stop hook: exit code 2 blocks the turn from ending until it passes.

"A check is the difference between watching a session and walking away from it." This is LEDGER's sensor idea, applied with a prompt and a hook.
Tip 2

Treat context as the budget

  • One task per session. /clear between unrelated tasks.
  • After two failed corrections, start fresh with a better prompt.
  • Send investigation to subagents so file dumps never enter the main thread.
  • Handoff: session bloated, work not done? Write state to disk and restart clean.
Use subagents to investigate how token refresh works and whether we have OAuth utilities to reuse. Return file:line refs and a 10-line summary.
Write HANDOFF.md: goal, files changed, decisions and why, approaches that failed and why, the exact next step, and the test command that proves it. # fresh session: @HANDOFF.md continue from the next step
Tip 3

Get a fresh-context review before "done"

The agent that wrote the code is biased toward it. Review with something that didn't write it:

/code-review subagenta second sessionCodex /review on Claude's branch
Use a subagent to review the diff against PLAN.md: every requirement implemented, edge cases tested, nothing out of scope. Report correctness gaps only.

Restrict findings to correctness and stated requirements, or you'll chase nitpicks into over-engineering.

Tip 4

Make repeated corrections durable

Correct the same thing twice? Encode it instead of correcting it a third time.
