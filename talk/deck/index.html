[Read the lanes top to bottom.] Here's the full lineage. A harness is everything around the model: context, reasoning, tools, permission, and the check. Every lane grew the same way: something outside the model worked, and then training pulled it in. Chain of thought is the clearest case. Asking PaLM to show its steps took grade-school math from 18% to 57%, but only at around 100 billion parameters. On small models it didn't help. Scale alone didn't find it, and the prompt alone didn't work. Then reinforcement learning trained the procedure into the weights, against a checker: DeepSeek's R1 was rewarded by rule-based checks, is the math answer right, do the tests pass. So the pattern isn't scaling, or RL, or harnesses. It's the coupling: the harness finds what works, training absorbs it, and scale makes it absorbable. Tools went the same way: ReAct, function calling, MCP, and now Claude Code, Codex and Antigravity running a simple loop. [→] What a model can't absorb is contact with the world: what's true right now, what it's allowed to touch, and what actually happened. [Point at the bottom lane.] Checking and recording is the thinnest lane. That's this talk.

Here's the mechanism behind that coupling, and it's my favorite pattern in the field: a harness produces training data. Its traces become training examples and its checks become rewards, so whatever procedure the harness runs, the next model learns. Wrappers become weights. [→ left column] Already happened. 'Think step by step' became reasoning models. Voting became self-checking. ReAct's text format became native tool calls. Tree search became learned backtracking. DeepSeek trained R1-Zero with reinforcement learning on two rule-based rewards: is the answer right, and is the format right. Nobody showed it how to backtrack. During training it started writing 'wait', going back and rechecking, and its answers got longer on their own. [→ right column] My guess for the next round: context compaction, subagents, skills and rules files, and plan search, including mine. GATS's planner is a procedure, so it can be absorbed too. [→ red card] What can't move inside is the check. Once a model trains against a verifier, the verifier becomes a target. That's Goodhart's law: when a measure becomes a target, it stops being a good measure. On ImpossibleBench, stronger models game tests more often, not less, and METR caught o3 reward hacking in 30% of its runs on one research benchmark. So the parts worth building outside the model are the ones it must not grade itself on: sensors, gates and the record.

Suppose those gaps closed. Start with arithmetic. At 99% per step, 100 steps succeed 37% of the time. Now add a check after every step that catches nine errors in ten. The error rate drops from one in a hundred to one in a thousand, [→] and 100 steps succeed 90% of the time. Same model. Put another way, the 37% cliff moves from step 100 to step 1,000. A check that catches 90% buys a ten times longer horizon; one that catches 99% buys a hundred times. That's math, not a benchmark, and it has one condition: the check has to fail independently of the model. A model grading its own work tends to miss the same things it got wrong. That's why the check lives outside. Close the other gaps and you get [→] horizons you can quote at 99% instead of 50%, [→] regression tests for agent behavior, and [→] agents regulated industries can actually audit. [→] Together: an agent you can leave running on a responsibility, not just a task. Next: how GATS and LEDGER go after these.

GATS is the planner, from my paper with my co-author, Dymitr Nowicki. Here's the problem it's built for. A NeurIPS 2024 paper trained a transformer on New York taxi rides; some of them probably drove past this building. It gave valid turn-by-turn directions through Manhattan almost every time. Then the authors pulled out the map it had learned: streets that don't exist, overpasses across the grid. Close 1% of the streets, and accuracy fell from nearly 100% to 67%. It learned routes, not the city. Today's agents are skilled sailors without a chart. They read the sea and estimate where they are, and the error grows every mile. GATS has a chart. [Point at the layers.] Tree search picks every action, over a graph of states that persists between runs. It uses UCB1, which scores each option by its average result plus a bonus for options it hasn't tried much. To predict what an action will do, it asks the cheapest layer that can answer. [→] Symbolic contracts first: exact and free. [→] Then statistics from its own past runs. [→] Only for a transition it's never seen, a cached LLM call. It plans the route before leaving, checks its position at every waypoint, and fixes the chart when the sea disagrees, so it doesn't hit the same rock twice. A repeat trip makes no LLM calls at all. [→] On a 12-category stress test it scores 100%, against 89% for LATS and 24% for ReAct, with zero LLM calls during planning. [→ live Llama 3.2] On a weak live model, LATS falls below 1%; GATS stays at 100%. [Say 'during planning' every time you say zero: 50 one-time bootstrap calls.]

LEDGER is the experiment: how reliable can a coding agent get if the model gets zero trust? In most agents the model decides what to do, does it, checks its own work and writes the report. LEDGER takes all of that away except one job: writing the patch. [Walk the pipeline.] [→] GATS plans every action. [→] The LLM writes a patch, nothing else. [→] Sensors decide what's true. [→] The journal records everything. Three rules. [→] It can't set state: whether tests pass, whether the repo is clean, whether a step can be undone, all of that comes from sensors. [→] It can't claim success: if what it says doesn't match what the sensors see, that's logged as an incident and the planner routes around it. [→] It can't pick or run actions: GATS picks them, risky ones go through gates, and when it's stuck it escalates with a named reason, like 'infeasible'. The cost is flexibility. It does far less than Claude Code. The question is how much reliability that buys. [→ terminal] This also answers the title. What did my agent actually do? I ask the record, not the model. 'ledger why' prints the search table it used to pick each step, recorded at the time, not an explanation written afterward. 'ledger replay' reproduces the run bit for bit. Each journal entry carries the hash of the one before it, so if anyone edits one field, 'verify-chain' shows where the chain breaks. Same guarantees on Claude, OpenAI or a local model. Where does this go? [→] First: in a company, the model is a part you'll swap every few months. I swapped Claude for a local 27B model and the guarantees didn't move, because they live in the harness: the state, the checks, the record. [→] Second: the harness is already an RL environment. Sensors are the reward signal, worktrees are the rollouts, and the journal holds the trajectories. Every action has a checked outcome, so you know which step earned the reward. [→] Third: self-improvement, with a gate. 'ledger improve' files its own bugs as failing tests and fixes them, using only a local model. The gate caught 2 bad changes out of 5. That's only safe while the checker sits outside the thing being improved. [→ bottom row] You don't need LEDGER to use this on Monday. Two rules first. Context degrades as it fills: 40 files in, the agent ignores the rule you gave it at the start. And without a pass/fail check, the agent stops when the work looks done, and you become the checker. So, four habits I use every day, with any agent. One: give every task a runnable check. Write the failing test first and ask it to end with the test output. [→] Two: treat context as a budget. One task per session, clear between tasks, send investigation to subagents, and write a handoff file when a session gets long. [→] Three: before you call it done, get a review from a fresh context: a review command, a second session, or another model, asking only for correctness gaps. [→] Four: when you correct the same thing twice, make it permanent. A judgment call goes in AGENTS.md, a repeated workflow becomes a skill, a mechanical rule becomes a hook. The two laws

Context is the budget.
A runnable check is the finish line.

Law 1: context degrades as it fills

Every file read and command output lands in the window. As it fills, the agent drops early instructions: 40 files and six suite runs in, it ignores the "no mocks" rule from turn 2.

Law 2: a check closes the loop

Without a pass/fail signal, the agent stops when the work looks done, and you become the verifier. With one, it iterates until the check passes.

Every tip that follows either protects context or closes the verification loop.

Tip 1

Give every task a runnable check

# before fix the rate limiter, it lets too many requests through # after Write a failing test in tests/rateLimiter.test.ts that fires 101 concurrent requests and expects exactly 100 x 200 and 1 x 429. Confirm it fails, fix the race, run `pnpm test rateLimiter` until green. End with the test output.

A concrete repro, a test that fails first, a scoped command, and evidence demanded instead of a claim. To make it unskippable, put make check in a Stop hook: exit code 2 blocks the turn from ending until it passes.

"A check is the difference between watching a session and walking away from it." This is LEDGER's sensor idea, applied with a prompt and a hook.
