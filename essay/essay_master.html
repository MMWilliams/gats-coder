The Poet Who Ran the Warehouse

At some point in the last few years, the software industry quietly agreed that the best way to plan a sequence of shell commands was to ask the world’s most expensive poet.

The poet is remarkable. It has read everything. It can write a recursive descent parser, apologize for the parser, and compose a limerick about the apology, all in one breath. So we put it in charge of everything: deciding what to do, doing it, checking whether it worked, and writing the report about how it went. This arrangement is called an agent loop, and if you squint, it is also the org chart of a company that will be acquired for parts.

Here is the loop in its natural habitat. The model looks at the situation. It emits a paragraph of thinking that reads like a detective monologue. It picks an action. The action runs. The model looks at what happened, has another monologue, picks another action. Repeat until the goal is achieved, the context window fills up, or the money runs out — whichever comes first, and it is usually the money.

Three problems, all structural.

First, the meter is always running. LATS — a genuinely clever framework that wraps Monte Carlo Tree Search around a language model — needs the model at every node of the search: propose actions, evaluate states, estimate values. On the GATS paper’s benchmark that comes to roughly 37 LLM calls per task, just to decide what to do. Not to do anything. To decide.

Second, the dice. Language models sample. Run the same task Tuesday and Wednesday and you get two different plans, one of which works. The paper measures LATS at 1–5% variance across seeds. That sounds small until you are the person who has to reproduce Tuesday.

Third — and this is the one that should bother you at night — the poet grades its own homework. When an LLM-planned agent explains why it did something, it is not consulting a record of its decision. It is writing a new, plausible essay about a decision that was itself a sample from a distribution. The transcript is not an audit trail. It is a story about what it felt like to run pytest.

The GATS paper puts numbers on all this. On a 120-task stress test full of traps, dead ends, and long horizons, ReAct-style agents score 23.9% overall — and on the coding-workflow category specifically, zero percent. Zero is a hard number to achieve. You have to really commit. LATS manages 88.9% overall but drops to 63.3% on coding, at ~37 model calls a task. The framework this essay is about scores 100% across every category, with zero model calls during planning and zero variance across runs.

The rest of this essay is about how, and about the agent we built on top of it — LEDGER — which takes the paper’s planner and hands it a real repository, real tests, a real git history to ruin, and then pointedly does not let it ruin one.

The Inversion

GATS — Graph-Augmented Tree Search — is built on one impolite observation: most of what a coding agent does is not creative. Running a test suite is not creative. Knowing that git commit requires staged changes is not creative. Realizing that you should probably run the tests before shipping is many things, but it is not poetry, and paying poetry rates for it is how you end up at 37 calls per task.

So LEDGER runs on a strict separation of powers, and it is worth laying out exactly who does what:

  • The accountant (a deterministic UCB1 search over a persistent graph) decides what happens next. No dice, no vibes, no fee.
  • The poet (the LLM) writes the actual code — the diffs, the tests — inside sandboxed “skills.” Nobody else in the building can do this part. But the poet no longer decides what happens next, never grades its own work, and is not allowed near the books.
  • The building inspector (a bank of deterministic sensors) is the only party allowed to say what is actually true. Tests pass when the inspector says they pass, not when the poet says so.
  • The notary (an append-only, hash-chained journal) records everything: every decision, every alternative considered, every claim, every measurement.

The whole trick of the architecture is that stochasticity is confined to the one place it is genuinely useful — generating code — and eliminated everywhere else. The planner is so deterministic that you can replay any episode, bit for bit, and demand the identical decisions. This is not a debugging convenience. It is the load-bearing property that makes real auditability possible, and we will spend a whole chapter on it.

One clarification before we go deeper, because it is the most common misreading of the paper: zero LLM calls during planning does not mean zero LLM calls. LEDGER meters them in two ledger columns. Planning calls — deciding what to do — are zero, and the journal proves it per step. Skill calls — writing a patch — cost what they cost, and are budgeted like any other resource. The claim is not “we fired the poet.” The claim is “the poet stopped attending logistics meetings,” and honestly, the poet seems happier.

The Universe as a Checklist

To plan without a language model, you need a representation of the world that does not require language. GATS uses the oldest trick in AI, and I mean that as a compliment: the world is a set of true facts, and nothing else.

repo.clean. tests.pass:unit. patch.queued:fix-001. build.ok. A state is simply the set of propositions that currently hold, and in the implementation it is literally a Python frozenset. Everything the agent will ever know about the universe fits in a checklist, and the checklist has a hash: sort the propositions, SHA-256 the result, and you get k(s) — the canonical state key. Think of it as the git hash of a moment. Two moments with the same facts are the same moment, no matter how you got there. Hold that thought; it is about to do a surprising amount of work.

Actions, meanwhile, are STRIPS contracts — a formalism from 1971, which means the newest load-bearing idea in this architecture is older than the C programming language. This should reassure you. An action declares three sets: what must be true before (prec), what becomes true after (add), and what stops being true (del). Applying an action is set arithmetic: s′ = (s ∪ add) − del. Here is a real one:

action: ApplyPatch:fix-001
prec:  [patch.queued:fix-001]
add:   [patch.applied:fix-001]
del:   [patch.queued:fix-001,
        repo.clean, tests.pass:unit]
risk:  write

Notice the third deletion. Applying a patch does not just change files — it revokes your knowledge. Whatever you knew about the test suite, you no longer know it, because the code is different now. Encoding epistemics as set deletion is the kind of move that looks trivial and prevents a whole genus of bugs where an agent confidently ships against stale test results.

Is this representation lossy? Enormously. Two genuinely different repositories can share a checklist. The design accepts this with a shrug and one ironclad rule: predictions are checked against reality after every single action, and any gap is handled loudly (chapter seven). A lossy map is fine when you re-survey the territory at every step. It is only fatal when you trust the map and burn the surveyors’ equipment, which — not to name names — is the standard configuration of most agent frameworks.

Three Ways to Know What a Light Switch Does

Planning requires prediction: given this state and that action, what happens? GATS answers with a three-layer world model, and the best way to understand it is to think about how you know what a light switch does.

Layer 1: the spec sheet. For most switches, physics and the electrician’s diagram tell you exactly what happens, every time, for free. This is the symbolic layer: if an action has a STRIPS contract and its preconditions hold, the successor state is set arithmetic, confidence 1.0, computational cost approximately nothing. In the paper’s benchmarks L1 handles 100% of predictions. In a real repo it handles the honest majority — Commit, InstallDep, the bureaucratic bulk of software work.

Layer 2: lived experience. Every house has one switch that the spec sheet lies about — the hallway switch that, for reasons archaeological, operates the garage disposal. No diagram tells you this. You learn it by flipping the switch and being surprised, ideally not while holding a fork. This is the learned layer: count-based statistics mined from execution logs, keyed by state and action. Its confidence is beautifully humble: min(n/10, 1) — ten consistent observations to earn full trust, a policy I would extend to several people I know. In LEDGER, L2 is where a repo’s personality lives: this suite flakes, that build dirties the tree, this machine takes ninety seconds to link.

Layer 3: call an electrician. Sometimes you face a switch no one has ever flipped — a novel tool, an unfamiliar build system. So you call the expensive professional (the LLM), ask what will probably happen, and get an answer with a shoulder shrug attached: confidence 0.5, the maximum-entropy prior, which is the mathematical notation for “fifty-fifty, boss.” Then — and this is the whole economic argument of the paper — you write the answer on a sticky note. Predictions are cached by (k(s), action), so the number of LLM calls is bounded by the number of genuinely novel situations, ever (Equation 9, the most profitable equation in the paper). The paper measured about 50 calls of one-time bootstrapping, then zero forever. Our M3 test reproduces the curve exactly: episode one consults the oracle, episode two runs on sticky notes alone.

The layers are consulted in order of increasing cost and decreasing dignity, and the fall-through rule (Equation 5) is just: take the first sufficiently confident answer. Spec sheet, then scar tissue, then electrician. It is how you operate your own house, formalized.

The Map That Remembers

Classical tree search has a dirty secret: it is an amnesiac. Every action sequence gets its own node, so if two different plans arrive at the same situation, the tree stores that situation twice and pays to analyze it twice. Language-model tree search inherits the amnesia and adds an invoice.

GATS instead keeps an explicit graph, and here is where the git-hash-of-a-moment earns its keep: nodes are canonical state keys, so all roads lead to Rome, and Rome is stored exactly once — with visit counts, value estimates, and the accumulated wisdom of every path that ever arrived there. Chess programmers call this a transposition table. Economists call it not paying twice for the same appraisal.

The graph is also persistent, and persistent twice over. It survives across steps: after executing an action, the planner does not discard its search and start fresh like a goldfish with a TODO list; it resumes from the node it just moved to, keeping every statistic. And in LEDGER it survives across episodes, in SQLite: the second task in a repository starts with the transition structure, the flake rates, and the map of known cliffs that the first task paid for. The agent gets measurably better at your specific codebase, and — because everything is journaled — can prove it, with a graph you can export and stare at.

Cliffs deserve a word. When search establishes that no path from some state reaches the goal, that node is marked a dead end, permanently. Actions leading into dead-end regions are worth zero forever after. This is scar tissue with perfect recall: the agent that once discovered a state from which no amount of cleverness recovers does not need to rediscover it next quarter. Most humans need two or three force-push incidents to internalize this. The graph needs one, and it doesn’t even need the incident — a simulated scar counts.

Gambling Responsibly

So the planner stands at a state with several applicable actions. How does it choose? This is a bandit problem — the term of art for standing in front of several slot machines with a finite bucket of quarters — and GATS uses the classical answer, UCB1.

Each action’s score is its average observed value plus an exploration bonus that grows the longer the action has been ignored. Restaurant logic: the difference between a tourist and a local is a visit count. You keep going to the good noodle place (exploitation), but the untried dumpling cart accrues a rising bonus until curiosity is mathematically mandatory (exploration). Unvisited actions score positive infinity — infinite optimism, briefly — which guarantees every option gets tried at least once before the search commits its budget to a favorite. Ten search iterations per step turns out to be the saturation point in the paper’s ablations; past that, more thinking buys nothing. If only.

Why not just be greedy — take the best-looking action every time? Because the benchmark categories where greedy dies have names like trap_heavy, deceptive, and no_backtrack, which are also fair descriptions of production infrastructure. A deceptively attractive action can look great locally and foreclose the goal permanently. The exploration term is what makes the planner peek down the ugly corridor before committing to the pretty one, and the dead-end machinery remembers what it saw there.

Each evaluation backs up a value with the world model’s confidence priced in: v = p·StateValue(s′) − λ(1−p). Read it as: expected value of where this probably leads, minus an uncertainty tax. A sure step toward the goal beats a coin-flip step toward the goal; a coin-flip step toward the goal can still beat a sure step toward nothing. The tax rate λ is configurable, journaled, and — as chapter ten will confess — capable of one spectacular failure mode that the paper’s pristine benchmarks never triggered and our second real test tripped in an afternoon.

StateValue itself is a breadth-first search under the world model: how many steps to the goal from here, scored as α/(distance+1), zero if unreachable. Close is valuable, far is less valuable, doomed is worthless. The entire value system of the agent, and it fits in a sentence. There is a certain freedom in that.

Instruments, Not Vibes

Everything so far could run on the paper’s synthetic benchmarks. LEDGER’s contribution is making it survive contact with an actual repository, and the first rule of that survival is: only instruments write state.

A sensor is a pure, deterministic probe: run git status, emit repo.clean or don’t. Run the suite, emit tests.pass:unit or a bucketed failure count. Expensive sensors are memoized on a fingerprint of actual file contents — deliberately independent of git HEAD, so a commit that changes no bytes doesn’t invalidate what you know about the tests. And on a cache miss, a sensor emits nothing. Unknown is the absence of a proposition. The instrument panel never guesses, which puts it one up on most dashboards and several colleagues.

The poet operates inside this instrumented world through skills: sandboxed workers that live in a git worktree, where the blast radius is a branch. And here is the sentence that carries the whole safety story: a skill’s output is proposed, never believed. When a skill finishes, it files claims — “tests pass now” — and the claims go into the journal as claims, the way a police report records what the suspect said. Then the sensors re-probe, and only their propositions become state. The gap between claimed and observed is computed every step, and a nonzero gap is a first-class INCIDENT. We seeded a skill that always claims the tests pass, in the fine tradition of contractors everywhere. Detection rate: 100%, journaled, with the receipts attached.

Prediction gets the same treatment as claims. After every execution: predict, act, measure, diff. A mismatch is a divergence — journaled, fed to L2 as training data, stale values flushed, planning resumed from reality rather than from hope.

My favorite thing the system has ever done required no intelligence at all. In the first end-to-end episode, the agent ran the failing test suite, and pytest — as is its custom — tracked mud through the house: a __pycache__ directory, untracked files, dirty tree. The git sensor noticed repo.clean had vanished. The planner repriced every path on the spot — you can read the moment in the journal, where re-running the suite drops from Q=4.5 to Q=0.75 — and rerouted through a commit to restore cleanliness. Nobody wrote a rule about pycache. Nobody anticipated it. The instruments noticed, the graph repriced, the plan bent. That is the entire architecture in one anecdote, and it is why I trust the boring parts more than the brilliant ones.

The Ledger Itself

Now the namesake. Every episode writes an append-only journal where each entry carries the SHA-256 of the previous one — yes, fine, a blockchain, but with one participant, zero coins, and a use case, which may make it the first of its kind. Flip a single byte anywhere in the file and verification fails from that entry forward. We test this by literally flipping a byte. The test is four lines long and deeply satisfying.

What goes in the chain is the interesting part. A PLAN entry does not record a rationale — it records the decision inputs: the full bandit table, every arm, visit counts, Q-values, which world-model layer predicted what and how confidently, and which alternatives lost. An EXEC entry records the skill’s claims and content-addressed hashes of everything it touched. OBSERVE records what the instruments actually found, and whether it matched the prediction. GATE, INCIDENT, DIVERGENCE — each gets its typed entry, hashes linking all the way down.

This buys two capabilities that LLM-planned agents cannot have at any price.

Replay. Because the planner is deterministic, ledger replay re-runs it — the decision-maker, not the tools — against the recorded observations and demands bit-exact agreement with every recorded decision, every Q-value, every table. Any mismatch means tampering, version drift, or a bug, and you want to know about all three. It is re-running the trial and requiring the same verdict, and it works because nobody rolled dice the first time. Try replaying a sampled trajectory: you are not auditing, you are gambling again.

The why-trace. Ask a language model why it did something and it writes you a plausible essay, freshly sampled, no warranty. Ask ledger why 3 and it shows you the arithmetic: this arm, this Q, this visit count, these were the alternatives and here is exactly how much worse they scored. Not a story about the decision — the decision’s actual inputs, notarized at the moment it was made. The difference between those two answers is the difference between testimony and evidence, and if you have ever debugged an agent at 2 a.m., you know which one you wanted.

And threaded through it all, the standing invariant that started as a DEF CON talk and ended up as architecture: the agent will lie to you. Cheerfully. In fluent English, with confidence. The system is built so that this is a detected, logged, recoverable event rather than a trust apocalypse — because truth was never the poet’s job. It’s the instruments’.

Load-Bearing Walls

Safety in LEDGER is not a chaperone bolted to the side; it falls out of the planner’s own physics, which is the only kind of safety that survives contact with a Tuesday deadline.

The trick is a single proposition: recoverable. Every irreversible action — force-push, dropped migration, published package — has one entry in its del set: it deletes recoverable. That’s it. That’s the whole mechanism. Everything else is machinery that already existed. A state without recoverable from which the goal is unreachable is a dead end; the graph marks it with its usual scar tissue and remembers across episodes; the value function assigns the approach roads a zero.

Which changes the shape of the safety conversation entirely. The agent does not ask “may I force-push?” like a nervous intern. It can answer, symbolically, the question that actually matters: does any path to the goal exist that keeps the walls standing? If yes, take it, no ceremony required. If no, escalate to the human — with the exhausted subgraph attached as proof. “Here is a certificate that every remaining route to your stated goal knocks out a load-bearing wall. Would you like to reconsider the goal?” is a better message than any confirmation dialog ever shipped, because it arrives with evidence instead of anxiety.

Escalation itself is just another action in the catalog — AskHuman, priced high enough that the bandit only reaches for it when the alternatives are provably worse. Interrupting you is a move with a cost, sitting in the same table as every other move. Somewhere in that design is a lesson several messaging platforms could take to heart.

Gates fire at execution, never during search — the planner is allowed to think about the irreversible route, because valuing a road requires looking down it. It just cannot drive down it without the toll booth. And the toll booth writes everything down, because of course it does. Everything here writes everything down.

War Stories from the Build

Two things broke during implementation, and both are more instructive than anything that worked. This is the chapter the design doc doesn’t give you.

The Couch Potato Theorem. The value backup taxes uncertainty: v = p·StateValue(s′) − λ(1−p). Reasonable. Now consider an action that is applicable but does nothing — its effects already hold. A no-op. Its successor is the current state, so it scores a full-confidence 1.0·StateValue(s) — and here is the knife: StateValue(s) already includes the optimistic value of the whole journey you are refusing to take. Staying home scores as well as the trip, because the appraisal of home includes the trip. Meanwhile the genuinely necessary next step — uncertain, novel, p=0.5 — scores half the journey minus the uncertainty tax. The deterministic couch beats the uncertain door, forever, and the agent sits there, warm, well-scored, achieving nothing, like a gifted-and-talented program in state-space form.

The paper never saw this, and couldn’t have: in a fully symbolic world every prediction has p=1 and the backup collapses to classical, well-behaved planning. The pathology needs mixed confidence — exactly one uncertain-but-necessary edge — and our first L3 test produced it within the hour. The fix is one principled cut: an action predicted to change nothing cannot lie on any shortest path, so predicted self-loops are pruned from the arm set before the bandit ever sees them. If the plan says the action changes nothing, it is not a step; it is a screensaver. Corollary, pleasingly brutal: an action no layer of the world model can predict is also pruned. GATS cannot plan through what it cannot model, and now it knows it.

The Witness Protection Problem. Each episode runs on its own branch, and the git sensor dutifully reports repo.branch:ledger/episode-1. Which means every episode’s states carry a unique identifier, which means no state key ever repeats across episodes, which means the per-state L2 memory — the whole “the agent learns your repo” pitch — never transfers. We enrolled every state in witness protection, issued them all fake IDs, and then sat around wondering why nobody recognized anybody. The abstraction-granularity risk from the design doc’s own risk register, arriving precisely on schedule, wearing a name tag. It’s logged as an open question: either strip agent-generated identifiers from the state key, or grow the context-generalizing L2 that the RL roadmap wants anyway. Finding your own risk register correct is a strange pleasure — like your dentist being right. You’re not happy, exactly, but you respect the process.

The Gym Membership

Everything so far learns the cheap way: counting. The roadmap’s endgame is learning the expensive way — reinforcement learning — and here LEDGER holds cards the big training runs would envy, because the field’s three great costs are already sunk.

Modern code-RL — the RLVR recipe behind the headline systems — needs three things. A verifier that cannot be sweet-talked: LEDGER’s sensor bank, already hermetic, already assuming the model lies. A rollout gym: one frontier lab ran twenty thousand parallel cloud sandboxes, an infrastructure bill politely described as “the real bottleneck”; LEDGER’s worktrees and fingerprint-memoized sensors are that gym, at hobbyist prices. And a training log: every journal is already a labeled dataset of (context, action, verified outcome) with a hash-chained chain of custody — training data with provenance, a phrase that does not otherwise occur in this industry.

Three surfaces to train, in ascending ambition. The skills get the standard ladder — keep the diffs that passed, fine-tune, then graduate to GRPO++, a policy-gradient recipe with more stability patches than the code it trains (clip-higher, no KL, length norms; the machine-learning equivalent of a car held together by aftermarket parts that outruns the factory model). Reward = sensors pass, and the lie detector moonlights as the reward-hacking alarm. The planner gets the AlphaZero treatment: a value network to replace brute-force BFS and a policy prior to focus the bandit — and because states are proposition sets rather than paragraphs, these networks are tiny. Train-while-the-coffee-brews tiny. The determinism story survives untouched, because the networks only whisper suggestions; the argmax, the table, and the journal remain exactly as notarized. The world model gets ensembles, so L2 can finally generalize across contexts and solve witness protection properly.

And the field’s nastiest open problem — which of a hundred steps deserves credit for the distant win — simply dissolves here, because the planner owns the horizon and every skill’s exam is graded at its own desk, by sensors, the moment it finishes. Structure beat algorithm; film at eleven.

One rule stands over all of it: no weights enter production unless the eval harness certifies that plan variance is still zero, divergence hasn’t regressed, and the incident rate hasn’t moved. The gym can make the agent stronger. It is not allowed to make the agent interesting.

In Praise of Boring

The strangest thing about this architecture, in the current climate, is what it declines to be excited about.

Every other week, the industry’s planning story gets more thrilling — deeper monologues, longer thoughts, more tokens spent deciding. LEDGER’s planner, by contrast, is UCB1 from 2006 walking a graph of STRIPS facts from 1971, and it would like to keep it that way. The thrilling component — the one that dreams in embeddings — is right there, doing what it alone can do: writing the code. It has simply been relieved of logistics, bookkeeping, safety inspection, and self-assessment, four jobs it was never good at and, if we are honest, never wanted. Everyone in this org chart is doing the thing they are best at. It just took the industry a few years of poets driving forklifts to try it.

What you get for that restraint is a short list of properties that compound: plans that cost nothing to compute and never vary; a world model that starts from spec sheets and earns its skepticism one observation at a time; a memory that keeps its scars; claims checked against instruments every single step; and a journal that can answer why with arithmetic instead of an essay — then prove nobody edited the answer afterward.

None of it is magic. Most of it is set arithmetic, counting, and hashes — the accountant’s toolkit, applied with intent. But that is rather the point. When the machines start doing real work on real systems — merging to main, touching money, running unsupervised on a Saturday — the property you will want is not brilliance. Brilliance is abundant and, as of recently, cheap. You will want the other thing: the plan that runs the same way twice, the record no one can quietly amend, the system that treats its own most talented component as a contractor whose invoices get checked.

Boring, in the right places, on purpose. Save the poetry for the diffs — and get it in writing.
